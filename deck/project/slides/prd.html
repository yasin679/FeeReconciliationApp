Development-ready PRD

Separate states, minimum data, explicit permissions

State models, one per question

Verification claimed → verified · Identification unmatched → candidate → matched · Allocation proposed → approved → posted · Receipt issued → adjusted · Reversal requested → applied

Minimum data entities

Payment source record · student claim · cash report · match candidate · allocation proposal + lines · ledger entry · receipt · reversal / correction · case · audit event

Permissions, by person

Student: own data only · Counsellor: report cash · Operations: match, propose, cases · Finance: import, verify, approve others’ work, reverse · Admin: roles and policy, no money

Open decisions owned by Finance

A-01 fee-component order · A-02 cash deposit window · A-03 match evidence standard · A-04 refund vs credit for excess · A-05 single-approval threshold · A-06 receipt numbering

Integrations: bank statement feed in, student-system posting out (idempotent). Non-functional: every action audited, role-filtered data, posting retry-safe, daily reconciliation export.

8 · Full PRD with 16 acceptance criteria and the payment decision matrix submitted alongside

The core design choice: the APM draft had one "status" field doing five jobs. I split it into one state machine per question, so "we know who paid" can never be confused with "the money is on the ledger". The entities are the minimum to answer an audit query: who decided, on what evidence, and what changed. The six open decisions are policy, not engineering; I have defaulted each to the safe option in the build (for example, no automatic fee component) so engineering is not blocked while Finance decides. Likely question: why not let Admin approve in a pinch? Answer: anyone who can change roles and also move money can grant themselves anything; keeping Admin off the money path is the cheapest control we have.
